# 05 — UI

## 1. Input form

```
┌────────────────────────────────────────────┐
│  Race Readiness Check                      │
│                                            │
│  Battery voltage      [ 4.10    ] V        │
│  Battery current      [ 0.5     ] A        │
│  Battery temperature  [ 25      ] °C       │
│  Charging duration    [ 60      ] min      │
│                         = 3,600 s          │  ← live conversion hint
│  State of charge      [ 50      ] %        │
│                                            │
│                [ Submit ]                  │
└────────────────────────────────────────────┘
```

- Numeric inputs with units shown next to each field, followed by a **Submit** button. Decimals and negative values are allowed, except for duration and state of charge (0–100 %).
- A live hint under duration shows the converted seconds.
- Submit is disabled until all fields are valid. Errors appear inline under the field (see [01-requirements.md](01-requirements.md) §1.1).
- While the check runs, show a spinner and stage progress: "Overcharge ✓ → Thermal … → Prediction".

## 2. Result — CAN PROCEED

```
┌────────────────────────────────────────────┐
│  ✅  CAN PROCEED                            │
│  All safety checks passed.                 │
│  Predicted efficiency: 98.2 %              │
└────────────────────────────────────────────┘
```

## 3. Result — DO NOT PROCEED

Red banner. One card per failed rule, each in the same fixed format: reason, recorded value(s), fire hazard threshold(s), and the stage that failed. Rule IDs (R1–R6) and reason codes (for example `OVERCHARGED`) are internal. They are **not shown** on screen; only the plain-language reason is. Thresholds are written as the **failing condition**, matching the brief's example (for example, "battery voltage fire hazard threshold: > 4.2 V"). The exception is Stage 3: the prediction card shows the predicted efficiency as the recorded value and the minimum as **required to pass** (for example, "required to pass: predicted efficiency ≥ 70 %"). Recorded values are shown without the calculation behind them.

```
┌──────────────────────────────────────────────────────────────┐
│  ⛔  DO NOT PROCEED                                           │
│                                                              │
│  Stage 1: Overcharge                                         │
│  Reason: Battery already overcharged                         │
│    Recorded (input):       battery voltage 5.00 V,           │
│                            battery current -1.20 A           │
│    Fire hazard threshold:  battery voltage > 4.2 V AND       │
│                            battery current < 0 A             │
│                                                              │
│  Comment: Your battery is at risk of fire hazard if you      │
│  start the race now.                                         │
└──────────────────────────────────────────────────────────────┘
```

Example with several thermal failures (`T_t = 30 °C`, duration 1 min = 60 s):

```
⛔ DO NOT PROCEED
 Stage 2: Thermal
 • Thermal stress from battery charging is at high risk
     Recorded (calculated):  dT/dt = 0.08333 °C/s
     Fire hazard threshold:  dT/dt > 0.03 °C/s
 • Heat is increasing at a very fast rate while the battery charges
     Recorded (calculated):  d²T/dt² = 0.001389 °C/s²
     Fire hazard threshold:  d²T/dt² > 0.0005 °C/s²
 • Heat exposure to the surrounding environment is too high
     Recorded (calculated):  T_chem = 5.00 °C
     Fire hazard threshold:  T_chem > 0.3 °C
 Comment: Your battery is at risk of fire hazard if you start the race now.
```

Example with a Stage 3 prediction failure. Stages 1 and 2 passed, the model passed its quality gates, and the predicted efficiency is 65 %:

```
⛔ DO NOT PROCEED
 Stage 3: Prediction
 • Predicted efficiency is too low, so the car cannot proceed into the race
     Recorded (calculated):  predicted efficiency = 65.00 %   (XGBoost model v1)
     Required to pass:       predicted efficiency ≥ 70 %
 Comment: Your battery is at risk of fire hazard during the middle of the race.
```

### 3.1 Message templates

The Rule and Code columns tell the code which template to use. Only the Message column is displayed.

| Rule | Code | Message |
|------|------|---------|
| R1 | `OVERCHARGED` | **Battery already overcharged.** Battery voltage: `{V} V`, battery current: `{I} A`. Battery voltage fire hazard threshold: `> 4.2 V`. Battery current fire hazard threshold: `< 0 A`. (Unsafe when both are true.) |
| R2 | `HIGH_DTDT` | **Thermal stress from battery charging is at high risk.** dT/dt: `{dTdt} °C/s`. Fire hazard threshold: `> 0.03 °C/s`. |
| R3 | `HIGH_D2TDT2` | **Heat is increasing at a very fast rate while the battery charges.** d²T/dt²: `{d2Tdt2} °C/s²`. Fire hazard threshold: `> 0.0005 °C/s²`. |
| R4 | `HIGH_TCHEM` | **Heat exposure to the surrounding environment is too high.** T_chem: `{Tchem} °C`. Fire hazard threshold: `> 0.3 °C`. |
| R5 | `LOW_EFFICIENCY` | **Predicted efficiency is too low, so the car cannot proceed into the race.** Predicted efficiency: `{eff} %` (XGBoost model v`{version}`). Required to pass: `≥ 70 %`. |
| R6 | `MODEL_NOT_VALIDATED` | **Efficiency model not validated, so the race cannot be cleared.** Tolerance accuracy: `{tol} %` (needs > 80 %), R²: `{r2}` (needs > 0.90). |

Threshold values in messages are filled in from `thresholds.yaml` at runtime, not hard-coded. Calculated values are shown to at least 4 significant figures, so that a small value like `0.000167` is not rounded to `0`.

### 3.2 Comment

A DO NOT PROCEED result ends with one fixed **Comment** line, chosen by the stage that failed. It is set in code by the Race Decision node, not written by the LLM.

| Failed stage | Comment |
|--------------|---------|
| Stage 1 (overcharge) or Stage 2 (thermal) | Your battery is at risk of fire hazard if you start the race now. |
| Stage 3 (predicted efficiency too low) | Your battery is at risk of fire hazard during the middle of the race. |
| Stage 3 (efficiency model not validated) | No comment. Nothing was predicted, so no fire-risk claim is made. |

A CAN PROCEED result has no comment.

## 4. Implementation

- **Frontend:** static HTML/CSS/JS in [`frontend/`](../frontend) (no build step). It validates input for fast feedback, but the backend validates again and makes every decision.
- **Backend:** FastAPI app in [`src/formulatech/api.py`](../src/formulatech/api.py). It serves the frontend at `/` and exposes:
  - `GET /api/config`: `input_limits` from `thresholds.yaml`, used for client-side validation.
  - `POST /api/check`: body `{voltage_v, current_a, temperature_c, duration_min, soc_percent}`. Returns `422 {errors: {field: message}}` for invalid input (no verdict, IN-4). Otherwise it runs the LangGraph pipeline and returns `{verdict, stages, failures, predicted_efficiency_pct, comment, summary, explanations, t_seconds}`, where each failure is a display card (`stage`, `stage_name`, `reason`, `recorded_kind`, `recorded`, `threshold_label`, `thresholds`).
- **Run:** `uv run python -m formulatech.ml.train` (once, to create the model), then `uv run uvicorn formulatech.api:app --reload` and open http://127.0.0.1:8000/. `OLLAMA_URL` and `OLLAMA_MODEL` override the Ollama defaults. If Ollama is not running, the template messages are used (NFR-2).
